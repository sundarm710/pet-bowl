# ADR-002: WAL record format

## 1. CRC covers the length as well as the body
**Decision:** crc32 is computed over `body_len` plus the body.
**Why:** The length decides where the next record starts, so it must not be trusted unchecked. Covering it means a record only validates with the exact length it was written with.
**Consequence:** 4 extra bytes hashed per record. A damaged length is detected even in cases a body-only CRC could miss.

## 2. All-zero bytes are never a valid record
**Decision:** The minimum body is 5 bytes (op + key_len), so length 0 is rejected before the CRC is checked.
**Why:** A crash can leave a zero-filled tail, and crc32 of empty input is 0, so a format allowing length 0 would accept zeros as valid empty records.
**Consequence:** A zero tail decodes as `CorruptRecord` and recovery truncates there. A genuine empty put is 13 bytes and not all zero, so it still round-trips.

## 3. MAX_BODY bounds one record
**Decision:** A record body may not exceed 16 MiB. `decode` rejects larger lengths and `encode` refuses to write them.
**Why:** A garbage length must not make the reader allocate or wait for gigabytes, and the writer must never produce a record the reader would reject.
**Consequence:** Oversize on read means corruption, and on write it means a caller bug. The limit is a policy constant; change it by ADR.
